# Kyivstar-bot

Telegram-бот для майстрів Київстар у м. Шостка (Сумська обл., Україна). Бот приймає список заявок (підключення, ремонт, налаштування) і зберігає їх у SQLite. Потім будує оптимальний порядок об'їзду автомобілем: менше кілометрів означає менше пального. Порядок враховує пріоритет і орієнтовний час візиту. Також бот дає змогу відмічати виконання і копіювати номер заявки та текст звіту.

- Вихідні вимоги: [description.txt](description.txt)
- План і статус етапів: [PLAN.md](PLAN.md). Перед початком етапу звірся з ним, після завершення онови статус.

## Стек

- JavaScript, ES modules, без TypeScript. Типи описуємо через JSDoc там, де це допомагає.
- Cloudflare Workers (Telegram webhook) + Cloudflare D1 (SQLite) + Cron Triggers.
- [grammY](https://grammy.dev): Telegram Bot framework, адаптер `webhookCallback(bot, "cloudflare-mod")`.
- OpenRouteService (ORS): геокодинг і матриця відстаней `driving-car`. Резервний геокодер: Nominatim (OSM).
- Vitest + `@cloudflare/vitest-pool-workers` для тестів.
- Wrangler для dev, деплою і міграцій D1. Конфіг: `wrangler.jsonc`.

## Команди

Інструкція для людини (налаштування й деплой) — у [README.md](README.md).

```bash
npm test               # vitest: юніт-тести + інтеграційні тести бота
npm run dev:poll       # локальний бот через long polling (тестовий токен з .dev.vars), без тунелів
npm run dev            # wrangler dev: локальний Worker + локальна D1 (--test-scheduled для cron)
npm run db:migrate:local
npm run db:migrate:remote
npm run deploy         # wrangler deploy
npm run webhook:set    # setWebhook з secret_token + setMyCommands (.env.production)
npx wrangler tail      # живі логи продакшну
node --env-file=.dev.vars scripts/check-geocoding.js samples/list.txt   # покриття геокодингу на реальних адресах
npx wrangler deploy --dry-run --outdir <tmp>   # перевірити, що воркер збирається
```

- `npm install` працює з `legacy-peer-deps` (див. `.npmrc`): npm 10 падає на peer-залежностях vitest.
- Miniflare 5 (beta) приймає опції в новому форматі, тому в тестах їх загортаємо в `convertV4MiniflareOptions`.

## Структура

```
src/

  config.js                # місто, налаштування за замовчуванням, ліміти
  bot/
    createBot.js           # збирає Bot; порядок реєстрації обробників важливий
    access.js              # middleware: лише приватні чати й активні майстри
    handlers/              # common, admin, upload, tickets, route, location, report, settings
    views.js               # картка заявки, маршрут, списки → { text, reply_markup }
    texts.js               # УСІ тексти інтерфейсу (українською)
    keyboards.js           # reply-клавіатури
    geoReport.js           # підсумок геокодингу майстру
  domain/                  # чиста логіка без I/O, покрита тестами
    parser.js              # розбір списку заявок
    address.js             # розбір адреси → ключ кешу
    optimizer.js           # порядок об'їзду
    geo.js                 # haversine
  services/                # зовнішні HTTP: ors.js, nominatim.js, geocoding.js (ланцюжок), routing.js, mapLinks.js
  jobs/                    # geocodeQueue.js (waitUntil + cron щохвилини), cleanup.js (cron щоночі)
  db/                      # репозиторії: users, tickets, geocache, templates, state
  lib/                     # time.js (Europe/Kyiv), html.js
migrations/                # 0001_init.sql, ... (лише додаємо нові, старі не редагуємо)
scripts/                   # dev-polling.js, set-webhook.js, check-geocoding.js
test/                      # *.test.js; helpers/harness.js — бот + Miniflare D1 + фейковий Telegram API
```

## Тести

- Юніт-тести: `parser`, `address`, `optimizer`, `geocoding` (`fetch` підміняємо через `vi.stubGlobal`).
- Інтеграційні тести (`test/bot.test.js`): реальний `createBot` поверх D1 у Miniflare. Telegram API підміняє transformer, `geocodeAddress` — `vi.mock`, без мережі. Helper `harness.send` / `press` / `location` надсилає апдейти. Helper `last` / `outgoing` повертає те, що бот надіслав.
- Кожна нова фіча бота повинна мати тест на сценарій користувача в `bot.test.js`.

## Конфігурація

- Секрети (`wrangler secret put` у продакшні, `.dev.vars` локально): `BOT_TOKEN`, `WEBHOOK_SECRET`, `ORS_API_KEY`.
- Змінні (`wrangler.jsonc` → `vars`): `ADMIN_IDS` (Telegram ID через кому), `BOT_INFO` (JSON з getMe), налаштування за замовчуванням (див. нижче).
- Binding D1: `DB`.
- `.dev.vars` у `.gitignore`. Секрети ніколи не комітимо. Приклад лежить у `.dev.vars.example`.

## Доменні правила

### Формат заявки

```
1.🟢 2262291418 — 09:01 | Свемівська, 4, кв. 67 (подкл)
2.🟡 2262293012 — 09:44 | Свемівська, 3, кв. 8 (рем)
```

Порядок частин:

1. порядковий номер `1.` (необов'язковий);
2. емодзі пріоритету;
3. номер заявки (лише цифри);
4. тире `—`, `–` або `-`;
5. час візиту `HH:MM`;
6. `|`;
7. адреса;
8. тип у дужках.

Правила парсера:

- Парсер толерантний до зайвих пробілів, відсутніх номера рядка, емодзі чи квартири. Розуміє `вул.`, `пров.`, `просп.`, будинки `4а` і `4/2`, різні апострофи (`'` `’` `ʼ`).
- Бот приймає і вставлений текст, і переслані повідомлення. В одному повідомленні може бути багато заявок.
- Рядок без номера з 6+ цифр ігнорується: це заголовки й коментарі. Рядок з таким номером, який не вдалося розібрати, бот показує користувачеві.
- Заявка повинна мати хоча б одну ознаку: час, `|` або тип у дужках. Інакше текст на кшталт «2262291418 переобжим абон» розпізнався б як заявка.
- Повторне завантаження робить upsert за `(user_id, number)` і оновлює поля, але статус «виконано» не скидає.
- Дата заявки дорівнює даті завантаження в `Europe/Kyiv`.

### Пріоритет

- Джерело істини: емодзі. 🟢 означає `1` (вищий, зазвичай підключення), 🟡 означає `2` (нижчий, зазвичай ремонт).
- Якщо емодзі немає, пріоритет визначає тип: `подкл`/`підкл` дає `1`, `рем` дає `2`, інше чи невідоме дає `2`.
- Тип зберігаємо двічі: сирий текст і нормалізоване значення `connect` | `repair` | `other`.

### Порядок об'їзду (гібридне правило)

1. Спочатку йдуть заявки пріоритету 1, потім пріоритету 2.
2. Виняток: заявка пріоритету 2 у межах `NEARBY_RADIUS_M` (типово 300 м по прямій) від заявки пріоритету 1 виконується одразу після неї. Разом вони утворюють кластер.
3. Усередині кожної фази мінімізуємо відстань за кермом. Відстані беремо з матриці ORS. Якщо вона недоступна, рахуємо haversine × 1.3 при 30 км/год.
4. Час візиту лише орієнтир. Якщо прогнозоване прибуття відхиляється від нього більше ніж на `TIME_SLACK_MIN`, додається м'який штраф. Правило пріоритету штраф ніколи не ламає.
5. Тривалість роботи на заявці: `SERVICE_MIN`, типово 40 хв, однакова для всіх типів.
6. Старт: фіксована точка майстра (дім чи склад) або поточна геолокація, надіслана перед побудовою маршруту. Маршрут відкритий, тобто закінчується на останній заявці.
7. Час виїзду: `max(зараз, WORKDAY_START)`. Якщо робочий день уже скінчився, береться початок наступного дня.

Оптимізатор живе в `src/domain/optimizer.js` як чиста детермінована функція без I/O. Алгоритм:

1. стартові порядки: nearest neighbour і сортування за часом візиту;
2. 2-opt і Or-opt;
3. запобіжник `maxWork` на випадок обмеження CPU.

Швидкість: 20 точок < 1 мс, 40 точок ≈ 5 мс. Кожна зміна алгоритму супроводжується тестами.

Після «⏭ Пізніше» заявка переходить у кінець порядку. Нові заявки скидають побудований маршрут, тож його треба перебудувати.

### Геокодинг

- Місто Шостка, центр ≈ `51.8667, 33.4833`. Результат далі 15 км від центру вважаємо «не знайдено».
- Кеш `geocache` спільний для всіх майстрів. Ключ: нормалізована адреса `вулиця|будинок`, квартира на ключ не впливає.
- Ланцюжок пошуку: кеш → ORS → Nominatim → прохання до майстра надіслати геоточку. Точка від майстра зберігається з `source = manual` і має найвищу довіру.
- `precision`:
  - `house` дає `geo_status = found`;
  - `street` дає `approx`: заявка йде в маршрут, але бот пропонує уточнити точку;
  - `none` дає `not_found`: «не знайдено» кешується на 7 днів.
- Якщо жоден геокодер не відповів, заявка лишається `pending`, і Cron повторить спробу.
- Стан очікування вводу (`user_state`) живе 30 хв. Список заявок завжди важливіший за очікуваний ввід.
- Nominatim: не більше 1 запиту на секунду, змістовний `User-Agent` без персональних даних.

### Звіт («прив'язаний текст»)

- Формат: `заявка #{number} {text}`, наприклад `заявка #2262291418 переобжим абон`.
- `text` береться зі списку шаблонів майстра (редагується в боті) або вводиться вручну.
- Копіювання: inline-кнопка з `copy_text` (Bot API 7.11+, до 256 символів). Той самий текст дублюємо в `<code>` для старих клієнтів.

### Користувачі

- Майстрів кілька. Кожен бачить лише свої заявки, маршрут, шаблони і налаштування. Кожен запит до БД фільтрується за `user_id`.
- Доступ визначає whitelist у таблиці `users`. Адміни задані в `ADMIN_IDS`.
- Невідомий користувач після `/start` потрапляє в запит до адміна з кнопками «Дозволити» і «Відхилити».

## Обмеження Cloudflare (Free plan)

- 10 мс CPU на запит, тому важких обчислень уникаємо. Оптимізатор для ≤40 точок у цей ліміт вкладається.
- Близько 50 зовнішніх subrequest на один виклик. Тому геокодинг іде батчами: частина в `ctx.waitUntil`, решта через Cron щохвилини.
- На webhook відповідаємо швидко. Довгі операції виконуємо в `waitUntil` або Cron.
- `botInfo` передаємо в `new Bot(token, { botInfo })`, щоб не викликати `getMe` на кожен запит.
- Worker працює в UTC. Усі дати й час рахуємо в `Europe/Kyiv` через `Intl`.

## Конвенції

- Код, ідентифікатори і назви файлів англійською. Тексти інтерфейсу українською і тільки в `src/bot/texts.js`.
- Коментарі українською, лише там, де неочевидно «чому».
- `parse_mode: "HTML"`. Увесь користувацький ввід і дані заявок екрануємо (`escapeHtml`).
- Повідомлення довші за 4096 символів розбиваємо на частини.
- SQL пишемо лише параметризованими запитами `prepare(...).bind(...)`. Схему змінюємо тільки новою міграцією.
- Доменна логіка (parser, address, optimizer) складається з чистих функцій з unit-тестами. Telegram, D1 і HTTP-клієнти є тонкими адаптерами навколо неї.
- Зовнішні сервіси (ORS, Nominatim) викликаємо через `services/` з таймаутом. Помилка провайдера не валить бота, а переводить на fallback.
